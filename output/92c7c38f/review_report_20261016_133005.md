# 评审报告

## 评分总览
- 总体评分：8.5 / 10
- PRD 评分：8.5 / 10
- 技术评分：8.5 / 10
- 是否通过：通过

## 问题列表

### [MEDIUM] 一致性
PRD 中「邮箱登录与令牌签发」将刷新令牌标注为「可选」，但技术设计将刷新令牌作为登录接口的固定返回字段（refresh_token、refresh_expires_in），并据此设计了 refresh_tokens 表、/refresh 接口与登出吊销逻辑。需求澄清 open_questions 中「是否需要刷新令牌机制」仍未明确回答，存在需求与设计不一致风险。
- 建议：在 PRD 中明确刷新令牌为必选能力（与设计对齐），或由设计提供「仅 Access Token」的降级开关，避免接口契约与实现不一致。
- 回流目标：solution

### [MEDIUM] 一致性
PRD「安全审计与日志」为 P2 优先级，但技术设计为其分配了独立服务（Audit & Logging Service）、audit_logs/login_attempts 两张表、审计查询接口与 MQ 异步链路，投入与优先级不匹配；同时 PRD 未定义审计日志的查询/管理接口需求，而设计新增了 /audit-logs 与 /rate-limit-policies 管理端点。
- 建议：在 PRD 中补充审计日志查询、限流策略管理等运维/管理侧功能模块与用户故事，或将设计中的管理端点标注为可选/后续迭代，保持优先级与范围一致。
- 回流目标：solution

### [MEDIUM] 完整性
PRD 的「RESTful API 接口层」子特性包含「统一错误码与错误信息」，但技术设计仅笼统提及 error_handler 与统一错误响应，未给出具体错误码清单（如 EMAIL_EXISTS、INVALID_CREDENTIALS、RATE_LIMITED、TOKEN_REVOKED 等）及其与 HTTP 状态码的映射表。
- 建议：在技术设计中补充完整的错误码字典与 HTTP 状态码映射表，并在 OpenAPI 文档中体现，确保接入方能准确处理错误。
- 回流目标：engineer

### [MEDIUM] 完整性
PRD 非功能需求要求「支持用户数据删除请求」，设计提供了 DELETE /users/{user_id} 软删除接口，但未说明软删除后邮箱唯一索引（WHERE deleted_at IS NULL）导致同一邮箱可被重新注册时的账号归属、审计日志与历史数据保留策略，也未说明数据删除的合规留存边界。
- 建议：补充软删除后的数据保留/匿名化策略、邮箱复用规则及审计日志留存与删除的合规处理说明。
- 回流目标：engineer

### [MEDIUM] 可实现性
PRD 要求「登录失败 5 次锁定 15 分钟」，设计同时使用 Redis 计数（以 Redis 为准）与 users.failed_login_count/locked_until 字段，存在双写一致性问题；风险项虽提出「定期对账」，但未定义对账机制与冲突解决策略。
- 建议：明确锁定状态的单一权威来源（建议 Redis 为准，DB 仅审计），或定义清晰的双写与对账流程，避免多实例下锁定行为不一致。
- 回流目标：engineer

### [MEDIUM] 可实现性
PRD 性能指标要求单实例 ≥ 5k QPS、集群 ≥ 50k QPS，且登录接口 P99 < 200ms；但密码哈希（bcrypt cost≥10/Argon2id）为 CPU 密集操作，设计虽提出线程池限流与水平扩展，却未给出单实例哈希吞吐估算与实例数推导，50k QPS 目标的可达性缺乏量化论证。
- 建议：补充基于哈希吞吐的容量估算（单实例可支撑的登录 QPS）、所需实例数与压测验证计划，明确 50k QPS 是整体接口还是仅令牌校验接口。
- 回流目标：engineer

### [LOW] 一致性
PRD 用户故事提到「运维/安全人员配置限流策略并查看认证服务运行指标」，但 PRD 功能模块列表中未单列「限流策略管理」模块，而设计提供了 rate-limit-policies 的查询与更新接口及配置表，功能归属在 PRD 中不清晰。
- 建议：在 PRD 中补充限流策略配置管理相关功能模块与用户故事，或明确其归属「高并发支撑能力」子特性。
- 回流目标：solution

### [LOW] 完整性
PRD 未定义 JWT 访问令牌与刷新令牌的具体有效期、签名算法（设计采用 RS256）、密钥轮换（kid）等关键参数，而这些直接影响安全性与客户端集成行为。
- 建议：在 PRD 或技术设计中明确令牌有效期、签名算法、密钥轮换策略等参数，并纳入 OpenAPI 文档。
- 回流目标：engineer

### [LOW] 其他
PRD 的 out_of_scope 明确排除权限与角色管理（RBAC），但设计中的 /audit-logs、/rate-limit-policies、DELETE /users/{user_id} 等管理端点仅标注 auth_required=true，未说明如何区分「安全管理员」与普通用户，与排除 RBAC 的范围存在潜在冲突。
- 建议：明确管理端点的鉴权方式（如独立管理令牌/网关白名单/简单管理员标识），避免与 out_of_scope 冲突。
- 回流目标：engineer


## 修订建议

- 明确刷新令牌是必选还是可选，统一 PRD 与接口契约（登录返回字段、/refresh 接口、登出吊销逻辑）。

- 补充完整的统一错误码字典与 HTTP 状态码映射，并写入 OpenAPI 文档。

- 为高并发目标补充基于密码哈希吞吐的容量估算与压测验证计划，量化 50k QPS 的可达性。

- 明确登录失败锁定状态的单一权威来源与对账机制，消除 Redis/DB 双写不一致。

- 补充用户数据删除（软删除）后的数据保留、邮箱复用与审计日志合规处理策略。

- 明确管理类端点（审计查询、限流策略、用户删除）的鉴权方式，避免与 out_of_scope 的 RBAC 排除冲突。

- 在 PRD 中补充审计日志查询与限流策略管理相关功能模块/用户故事，使优先级与设计范围一致。


## 评审总结
整体方案质量较高，PRD 与技术设计在功能模块、API 端点与数据库表三个层面建立了清晰可追溯的映射：9 个功能模块全部在 api_endpoints（13 个端点）与 db_schema（8 张表）中有对应覆盖，API 覆盖率与 DB 覆盖率均达到 1.0，满足硬性评审规则。架构采用无状态认证服务 + 网关 + Redis + MQ，与 PRD 的高并发、可水平扩展定位一致；技术风险识别全面（令牌吊销窗口、Redis 单点、哈希 CPU 瓶颈、暴力破解等）并给出合理缓解措施。主要问题集中在需求与设计的细节一致性（刷新令牌可选性、审计/限流管理功能的优先级与归属）、统一错误码缺失、锁定状态双写一致性、以及 50k QPS 目标的量化论证不足。以上均为中低严重度问题，无 critical 缺陷，不阻塞进入下一阶段，建议在实现前按建议逐项收敛。
